# Milestone Plan: v1.49 Canonical Runtime Contract And Governance Modes

**Status:** Active
**Created:** 2026-04-10

## Goal

Rewrite the active architecture, governance, and evolution contract to match what the Rust runtime actually ships, including identity admission, human gates, consensus receipts, degraded governance, and partition behavior.

## Requirements

- **CONTRACT-01**: active-vs-historical doc matrix and source-of-truth contract
- **CONTRACT-02**: canonical capability matrix across critical, async, governance, evolution, and operator lanes
- **CONTRACT-03**: agent/config/operator docs align with the Rust runtime rather than historical Python seams
- **GOVMODE-01**: governance modes cover local guarded response, human gates, receipt-backed quorum, and maintenance-only behavior
- **GOVMODE-02**: identity admission, rotation, human-gate severity, and approval lineage are defined in one active contract
- **GOVMODE-03**: degraded governance, contingency leases, partition handling, reconciliation, and trust recovery are fail-closed and operator-visible
- **EVOCONTRACT-01**: queue, canary, promotion, proof, and review artifacts are restated as one bounded evolution contract

## Proposed Phase Structure

Starting from phase 164 (v1.48 ends at 163).

### Phase 164: Canonical Capability Matrix And Source-Of-Truth Reset
**Goal**: Align the planning layer, canonical docs, and repo-owned config around one active runtime shape.
**Requirements**: CONTRACT-01, CONTRACT-02
**Success Criteria**:
1. Active and historical documents are explicitly separated without contradictory claims.
2. One capability matrix covers critical lane, async lane, governance, evolution, and operator surfaces.
3. Canonical docs and planning docs point at the same runtime and deployment surfaces.

### Phase 165: Governance Modes And Identity Admission Contracts
**Goal**: Canonicalize the shipped governance model from local guarded response through receipt-backed quorum and identity admission.
**Requirements**: CONTRACT-03, GOVMODE-01, GOVMODE-02
**Success Criteria**:
1. Governance modes define when human gates, consensus receipts, and identity admission apply.
2. Identity rotation, registry admission, and approval lineage are documented in one active contract.
3. Config and status surfaces reference the same governance semantics.

### Phase 166: Degraded Governance And Partition Recovery Spec
**Goal**: Restate the shipped degraded-governance and partition behavior as explicit fail-closed contracts.
**Requirements**: GOVMODE-03
**Success Criteria**:
1. Degraded committee health, contingency lease redemption, and partition reconciliation are specified against current runtime behavior.
2. Partition-era observability, denied-action handling, and recovery markers are operator-visible and auditable.
3. The spec clearly marks what remains deferred.

### Phase 167: Evolution, Rollout, And Operator Contract Consolidation
**Goal**: Reframe the shipped evolution and rollout path as one canonical operator contract.
**Requirements**: EVOCONTRACT-01
**Success Criteria**:
1. Queue, canary, promotion, proof, and review artifacts are described as one bounded state machine.
2. The contract explains what is automatic, what is gated, and what remains advisory-only.
3. Evolution status, proof exports, and review surfaces align with the written contract.
