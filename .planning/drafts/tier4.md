## v1.37 Requirements: Persistence And Supply Chain Detection

- [ ] **PERSIST-01**: A `PersistenceDetector` implements `DetectionStrategy` and identifies suspicious scheduled task creation, cron entry modification, systemd timer installation, and registry run key writes from `TelemetryEvent` payloads using two new `TelemetryPayload` variants: `RegistryPersistence` (carrying `registry_path`, `value_name`, `value_data`, `access_type`, and `process_name`) and `FilePersistence` (carrying `file_path`, `operation`, `process_name`, and `content_preview`).
- [ ] **PERSIST-02**: A `SupplyChainDetector` implements `DetectionStrategy` and identifies unsigned binaries executing from trusted paths (e.g. `C:\Windows\System32`, `/usr/bin`), DLL side-loading patterns where a known-good process loads a library from an unexpected directory, and signed-binary abuse (certutil with `-urlcache`, rundll32 with remote or `javascript:` arguments) from `ProcessStart` and `FilePersistence` telemetry events.
- [ ] **PERSIST-03**: The `ThreatClass` enum in `swarm-core::pheromone` includes `Persistence` (already present) and a new `SupplyChain` variant; both detectors tag every `DetectionFinding` with a `mitre_technique_id` field in the `evidence` JSON object (e.g. `"T1053.005"` for scheduled tasks, `"T1574.001"` for DLL search-order hijacking).
- [ ] **PERSIST-04**: Both detectors are configurable via `PersistenceProfile` (fields: `suspicious_registry_run_paths: Vec<String>`, `suspicious_cron_directories: Vec<String>`, `dormancy_window_secs: u64`, `high_confidence_threshold: f64`, `medium_confidence_threshold: f64`) and `SupplyChainProfile` (fields: `trusted_paths: Vec<String>`, `trusted_signers: Vec<String>`, `suspicious_loader_pairs: Vec<(String, String)>`, `high_confidence_threshold: f64`, `medium_confidence_threshold: f64`), with `validate()` returning `ProfileValidationError` consistent with existing profiles.
- [ ] **PERSIST-05**: Integration tests construct synthetic `RegistryPersistence`, `FilePersistence`, and `ProcessStart` telemetry events, evaluate them through `PersistenceDetector` and `SupplyChainDetector`, assert that the resulting `DetectionFinding` records carry the correct `ThreatClass` and `mitre_technique_id`, and convert findings to `PheromoneDeposit` entries via `findings_to_deposits` with non-zero confidence.

## v1.38 Requirements: Fileless Execution And Behavioral Baselines

- [ ] **FILELESS-01**: A `FilelessExecutionDetector` implements `DetectionStrategy` and identifies indicators of reflective DLL injection (allocation with `PAGE_EXECUTE_READWRITE` from a non-system process), encoded PowerShell execution with multi-stage deobfuscation hints (nested `FromBase64String`, `Invoke-Expression` chains), and raw syscall gadget patterns from a new `TelemetryPayload::ProcessMemoryAccess` variant and existing `ProcessStart` events.
- [ ] **FILELESS-02**: A `BehavioralAnomalyDetector` implements `DetectionStrategy` and maintains per-host process ancestry baselines (observed parent-child pairs and per-user binary sets); it flags deviations such as an unusual parent spawning a known tool, a first-seen binary on a host, or atypical tool usage for a user role as medium-confidence `DetectionFinding` records with `strategy_id` `"behavioral_anomaly"`.
- [ ] **FILELESS-03**: `TelemetryPayload` in `swarm-whisker::detector` includes a `ProcessMemoryAccess` variant carrying `ProcessMemoryAccessEvent` with fields `source_process: String`, `target_process: String`, `allocation_type: String`, `protection_flags: String`, `region_size: u64`, and `call_stack_hint: Option<String>` for memory-based detection heuristics.
- [ ] **FILELESS-04**: `BehavioralAnomalyDetector` baselines persist across runtime restarts by serializing the per-host state as pheromone deposits with `ThreatClass::Custom("behavioral_baseline".into())` in the durable `PheromoneSubstrate`; baseline entries decay with a configurable `baseline_half_life_secs` field in `BehavioralAnomalyProfile`, and the detector reconstructs its working state from surviving deposits on startup.
- [ ] **FILELESS-05**: `ThreatClass::DefenseEvasion` (already present) is used for fileless execution findings; a new `ThreatClass::PrivilegeEscalation` variant (already present) is used when `FilelessExecutionDetector` observes memory manipulation targeting a higher-privilege process, ensuring both threat classes appear in the `DetectionFinding.threat_class` field as appropriate.
- [ ] **FILELESS-06**: Both detectors ship with configurable profiles: `FilelessExecutionProfile` (fields: `entropy_threshold: f64`, `suspicious_protection_flags: Vec<String>`, `high_confidence_threshold: f64`, `medium_confidence_threshold: f64`) and `BehavioralAnomalyProfile` (fields: `baseline_half_life_secs: f64`, `baseline_age_window_secs: u64`, `anomaly_sensitivity: f64`, `min_observations_before_alert: usize`, `high_confidence_threshold: f64`, `medium_confidence_threshold: f64`); integration tests cover reflective injection, encoded multi-stage PowerShell, first-seen binary, and unusual parent-child scenarios end-to-end through `evaluate` to `PheromoneDeposit`.

## v1.39 Requirements: Adversarial Robustness And Evasion Bench

- [ ] **EVASION-01**: An evasion test corpus under `tests/evasion/` provides at least 10 curated `TelemetryEvent` payloads per `ThreatClass` (covering `Execution`, `DataExfiltration`, `LateralMovement`, `CredentialAccess`, `Persistence`, `SupplyChain`, `DefenseEvasion`) representing real-world evasion techniques including command-line obfuscation, parameter reordering, timing manipulation between events, tool substitution (e.g. `certutil` replaced by `bitsadmin`), and case/encoding variation.
- [ ] **EVASION-02**: A coverage metrics module computes per-detector evasion catch rates (percentage of evasion corpus payloads that produce at least one `DetectionFinding` at any `Severity`) and exposes results via the operator API `/metrics` endpoint as `swarm_evasion_catch_rate{detector, threat_class}` gauge metrics and via a structured JSON response on `/api/v1/evasion/coverage`.
- [ ] **EVASION-03**: An automated strategy mutation module consumes evasion test failures (corpus payloads that produced zero findings), proposes `DetectorProfilesConfig` threshold adjustments (lowering confidence thresholds, adding new indicator patterns, expanding allowlists) as serialized profile diffs, and validates each mutation by running it through the existing `CanaryConfig` canary pipeline to confirm the mutation does not increase false-positive rates above a configurable `max_fp_rate: f64` before marking it promotable.
- [ ] **EVASION-04**: An evasion catalog file at `rulesets/evasion_catalog.toml` documents, for each `DetectionStrategy` implementation, which ATT&CK technique IDs the detector intentionally does not cover, with a required `rationale` string field per entry explaining the false-positive-rate vs. coverage trade-off decision.
- [ ] **EVASION-05**: Integration tests execute the full cycle: load the evasion corpus, run all registered `DetectionStrategy` implementations against it, identify coverage gaps where catch rate falls below a configurable `min_catch_rate: f64`, trigger strategy mutation proposals for failing detectors, validate mutations through the canary pipeline, and assert that at least one mutation proposal is produced and passes canary validation for each gap identified.
