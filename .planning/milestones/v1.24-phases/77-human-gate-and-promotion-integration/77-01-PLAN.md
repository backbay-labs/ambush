Modify `crates/swarm-runtime/src/promotion.rs`:

1. **Add `HumanApprovalPending` to `ProductionPromotionStatus`:**
   Add the variant after `Active`. Update any match arms that need to handle it (the existing `finalize_run` already matches on `Active` -- extend to also accept `HumanApprovalPending` for halt/rollback since operators must be able to abort pending promotions).

2. **Add approval reference types:**
   ```rust
   /// Reference to a signed approval vote for one promotion.
   #[derive(Debug, Clone, Serialize, Deserialize)]
   pub struct PromotionApprovalVoteRef {
       pub voter_id: String,
       pub public_key_hex: String,
       pub signature_hex: String,
       pub approved_at_ms: i64,
       pub ledger_entry_id: String,
   }

   /// Durable consensus receipt linking a promotion to its approval verdict.
   #[derive(Debug, Clone, Serialize, Deserialize)]
   pub struct PromotionConsensusReceipt {
       pub receipt_id: String,
       pub approval_set_id: String,
       pub verdict_id: String,
       pub ledger_id: String,
       pub threshold_met: bool,
       pub vote_count: usize,
       pub threshold_required: usize,
       pub receipt_signature_hex: String,
       pub receipt_signer_key_id: String,
       pub created_at_ms: i64,
   }

   /// Review packet persisted when a promotion enters human-approval-pending state.
   #[derive(Debug, Clone, Serialize, Deserialize)]
   pub struct PromotionPendingReviewPacket {
       pub gate_reason: String,
       pub severity: Severity,
       pub canary_run_id: String,
       pub promoted_strategy_id: String,
       pub canary_recommendation: CanaryRecommendation,
       pub pending_since_ms: i64,
   }
   ```

3. **Add new fields to `ProductionPromotionReport`:**
   - `pub pending_review: Option<PromotionPendingReviewPacket>` -- populated when status is HumanApprovalPending
   - `pub approval_votes: Vec<PromotionApprovalVoteRef>` -- populated when approval is granted
   - `pub consensus_receipt: Option<PromotionConsensusReceipt>` -- populated when approval is granted
   - `pub approval_severity: Option<Severity>` -- the severity that triggered the gate (always set for all promotions, None only for legacy records)

4. **Add `HumanApprovalPending` recommendation variant:**
   Add `PendingHumanApproval` to `ProductionPromotionRecommendation`.

5. **Modify `start_run()` to apply the severity gate:**
   After building the `ProductionPromotionAssignment`, determine the candidate severity. Use the `CanaryRunReport`'s findings to extract the max severity. If the max finding severity is `Severity::Critical`, set `status: ProductionPromotionStatus::HumanApprovalPending` and `recommendation: ProductionPromotionRecommendation::PendingHumanApproval` instead of `Active`/`Observing`. Populate `pending_review` with a `PromotionPendingReviewPacket`. For non-critical, keep existing behavior. Initialize `approval_votes: Vec::new()`, `consensus_receipt: None`, and set `approval_severity: Some(severity)`.

   The severity determination: if the canary report's `recommendation` is `ReadyForPromotionReview` and `assignment.candidate_strategy_id` strategy's findings from the canary metrics include any critical-severity detections, OR if the config explicitly marks the promotion as critical-severity, gate it. For simplicity, use a helper `fn promotion_severity(assignment: &ProductionPromotionAssignment) -> Severity` that checks the canary report's most severe finding preview. If not available from canary, check the underlying experiment. Default to `High` if unclear (fail-safe: only Critical gates).

   Actually, simpler: the severity is a property of the promotion context, not the individual findings. Add an optional `severity_override: Option<Severity>` parameter to `start_run()`. If the override is `Critical`, or if the canary report's most severe recent finding is Critical, gate it. This way operators can explicitly flag critical promotions.

   **IMPORTANT**: Do NOT change the `start_run` function signature in a breaking way. Instead, add a new `start_run_with_severity` method that accepts an optional severity. Have `start_run` call `start_run_with_severity(canary_results_dir, canary_run_id, None)` to preserve backward compatibility. When severity is None and cannot be inferred, default to non-gated (existing behavior).

6. **Add `approve_pending_run()` to `DefaultProductionPromotionHarness`:**
   ```rust
   pub fn approve_pending_run(
       &self,
       promotion_id: &str,
       votes: Vec<PromotionApprovalVoteRef>,
       consensus_receipt: Option<PromotionConsensusReceipt>,
       reason: &str,
   ) -> Result<ProductionPromotionLookup, ProductionPromotionError>
   ```
   Loads the promotion, verifies status is `HumanApprovalPending`, transitions to `Active`/`Observing`, sets `approval_votes`, `consensus_receipt`, clears `pending_review`, records the approval event, and persists. Returns error `RunNotPending` if the promotion is not in pending state.

7. **Add `RunNotPending` error variant** to `ProductionPromotionError`:
   ```rust
   #[error("production promotion `{promotion_id}` is not pending human approval (status `{status:?}`)")]
   RunNotPending { promotion_id: String, status: ProductionPromotionStatus },
   ```

8. **Update `finalize_run()` (halt/rollback):**
   Currently checks `status != Active` and returns `RunNotActive`. Expand to also accept `HumanApprovalPending` -- operators must be able to halt or roll back a pending promotion.

9. **Update `render_production_promotion_report()`:**

   - If `approval_votes` is non-empty, render "Approval Votes" section listing voter IDs and timestamps
   - If `consensus_receipt` is Some, render "Consensus Receipt" section with receipt ID, verdict, threshold, and signature

10. **Update `ProductionPromotionRecord::from_report()`** -- no structural change needed since it already copies status and recommendation. Ensure the new status/recommendation variants serialize correctly.
