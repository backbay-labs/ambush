# Milestone v1.2: Async Investigation And Correlation

**Status:** SHIPPED 2026-04-03
**Phases:** 8-10
**Total Plans:** 3

## Overview

`v1.2` added the first async enrichment and incident-assembly layer on top of the durable Rust runtime without contaminating the proven hot path. Replay bundles now seed background investigations, investigations roll up into explainable incidents, and operators can inspect the full chain from one review report.

## Phases

### Phase 8: Async Investigation Pipeline

**Goal:** Add a background investigation lane that enriches prior findings without delaying the original decision path.  
**Depends on:** 06, 07  
**Plans:** 1

Plans:
- [x] 08-01: Async investigation queue, durable bundle storage, and runtime submission seam

**Details:**
- Detect-only and live-response flows can emit an investigation request and complete the original decision path without waiting for enrichment.
- Operators can configure investigation enablement, worker count, concurrency, and time budgets through repository-owned config.
- Investigation outputs persist as durable bundles linked to the originating hunt ID and receipt IDs.
- Tests prove that investigation failure or timeout degrades to visible async status rather than blocking the hot path.

### Phase 9: Correlation And Incident Assembly

**Goal:** Group related findings and investigation bundles into reviewable incidents with explainable inclusion logic.  
**Depends on:** 08  
**Plans:** 1

Plans:
- [x] 09-01: Deterministic incident assembly and durable incident storage

**Details:**
- Runtime can assemble a correlated incident record from multiple findings and investigation bundles using stable identifiers, time windows, and shared evidence.
- Correlation output records which inputs were included, which were rejected, and why.
- Incident records persist across restart and remain linked to the underlying hunts, receipts, and investigation bundles.
- Tests cover both successful grouping and rejection cases so false merges are visible and bounded.

### Phase 10: Operator Review Surfaces

**Goal:** Expose investigation and incident context in one operator-facing surface with clear hot-path versus async boundaries.  
**Depends on:** 08, 09  
**Plans:** 1

Plans:
- [x] 10-01: Unified operator review report with freshness markers and warnings

**Details:**
- One operator-facing surface reports investigation queue state, recent job status, summaries, and failure reasons without requiring raw file inspection.
- Operators can inspect correlated incidents, underlying findings, and linked evidence from that same surface.
- Hot-path decisions and later async enrichment show distinct timestamps and freshness markers so operators can see what is authoritative versus newly attached context.
- Operator documentation covers how to review enriched findings, interpret incident membership, and handle degraded investigation states.

## Milestone Summary

**Key Decisions:**
- Replay bundles remain the seed artifact for all async enrichment.
- Correlation stays deterministic and operator-context-first.
- Operator review extends the existing status report instead of adding a second review API.

**Issues Resolved:**
- Added durable investigation storage and lookup by hunt or receipt ID.
- Added explainable incident assembly with explicit rejected candidates.
- Added one review report that distinguishes hot-path decisions from later enrichment.
- Added one config-backed runtime composition root for substrate, replay, investigation, and incident wiring.

**Issues Deferred:**
- Correlation still does not influence automated response policy.
- No CLI/HTTP operator console yet.
- No distributed governance or multi-node coordination.

**Technical Debt Incurred:**
- Nyquist validation files were not generated for phases 08-10.
