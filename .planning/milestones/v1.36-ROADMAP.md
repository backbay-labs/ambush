## Phase Details

### Phase 108: Canonical SIEM Forward Adapter
**Goal**: Add one canonical SIEM finding delivery contract and a resilient transport adapter for Splunk, ELK, and Chronicle
**Depends on**: Phase 107 (v1.35 complete)
**Requirements**: SIEM-01
**Success Criteria** (what must be TRUE):
  1. `SiemForwardConfig` selects Splunk HEC, ELK bulk ingest, or Chronicle transport through repo-owned config
  2. `SiemForwardAdapter` implements `ResponseExecutor` and serializes findings into one canonical `swarm_finding` JSON schema
  3. The adapter inherits retry, circuit-breaker, and dead-letter behavior through the existing `ResilientExecutor`
  4. The live runtime can forward findings through the configured SIEM adapter even when no response action is proposed
  5. Focused tests prove canonical payload delivery from the runtime hot path
**Plans**: 2/2 plans complete

Plans:
- [x] 108-01-PLAN.md -- Add canonical `swarm_finding` schema plus configurable Splunk, ELK, and Chronicle SIEM adapter support
- [x] 108-02-PLAN.md -- Integrate SIEM forwarding into the live runtime path and prove canonical finding delivery

### Phase 109: Finding Enrichment And Delivery Metadata
**Goal**: Enrich outbound findings with ancestry, host metadata, and detection latency before replay persistence and external delivery
**Depends on**: Phase 108
**Requirements**: SIEM-02
**Success Criteria** (what must be TRUE):
  1. `FindingEnrichmentService` attaches `parent_process_ancestry`, `host_metadata`, and `time_to_detect_ms` to every delivered finding
  2. Enrichment happens before replay persistence and outbound delivery so replay bundles and sinks share one evidence shape
  3. The enrichment path is deterministic and uses only live event context
  4. Canonical SIEM forward payloads include the enriched evidence
  5. Focused tests prove enriched findings survive runtime processing and delivery
**Plans**: 2/2 plans complete

Plans:
- [x] 109-01-PLAN.md -- Add shared finding enrichment before replay persistence and outbound delivery
- [x] 109-02-PLAN.md -- Prove enriched finding evidence reaches replay bundles and canonical SIEM delivery

### Phase 110: Notification Channels And Routing Rules
**Goal**: Add repo-owned notification channel config and rule-based finding routing for operator alert delivery
**Depends on**: Phase 109
**Requirements**: SIEM-03, SIEM-04
**Success Criteria** (what must be TRUE):
  1. `SwarmConfig.notification_channels` defines named channels with target URL, optional auth token, rate limit, and quiet hours
  2. Notification channel auth tokens support the existing `@secret:` resolution path
  3. A `RoutingRule` DSL matches findings by severity threshold, threat class, and UTC time-of-day range
  4. Matched rules fan out findings to one or more named channels without going through the response-action policy gate
  5. Focused tests prove matched findings route to the expected channels
**Plans**: 2/2 plans complete

Plans:
- [x] 110-01-PLAN.md -- Add notification channel config, validation, and secret-aware sender scaffolding
- [x] 110-02-PLAN.md -- Implement finding routing rules and runtime notification fan-out

### Phase 111: Dedup, Rate Limit, And Notification Dead-Letter Replay
**Goal**: Make notification delivery production-safe with dedup, rate limiting, dead-letter replay, and milestone closeout
**Depends on**: Phase 110
**Requirements**: SIEM-05, SIEM-06
**Success Criteria** (what must be TRUE):
  1. A dedup layer merges findings sharing `strategy_id` and `ThreatClass` within `dedup_window_ms` into one aggregated notification
  2. Each channel enforces an in-memory rate limit and writes suppressed alerts to a channel-specific `DeadLetterJournal`
  3. The protected operator surface lists and replays suppressed alerts at `/v1/notifications/dead-letter/{channel}`
  4. Configuration docs describe SIEM forward config, notification channels, routing rules, dedup, and replay behavior
  5. Milestone verification closes `v1.36` only after delivery, replay, and operator-surface behavior are proven
**Plans**: 2/2 plans complete

Plans:
- [x] 111-01-PLAN.md -- Add deduplication, per-channel rate limiting, and replay-ready notification dead-letter persistence
- [x] 111-02-PLAN.md -- Expose dead-letter list/replay on the operator surface and close the milestone with docs and verification
