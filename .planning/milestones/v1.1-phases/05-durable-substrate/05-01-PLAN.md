# Phase 5 Plan 01: Durable Substrate

<objective>
Add a self-contained durable substrate backend and wire fail-closed live-response readiness on top of it.
</objective>

<read_first>
- .planning/phases/05-durable-substrate/05-CONTEXT.md
- .planning/REQUIREMENTS.md

- crates/swarm-pheromone/src/substrate.rs
- crates/swarm-runtime/src/service.rs
- rulesets/default.yaml
</read_first>

<tasks>
<task number="1" type="auto">
<description>Extend the config contract with substrate backend selection and durable-live-response gating.</description>
<acceptance_criteria>
- Repository config can express in-memory and local-journal substrate backends.
- Invalid durable-live-response combinations fail validation.
- Existing repository config remains loadable with explicit defaults.
</acceptance_criteria>
</task>

<task number="2" type="auto">
<description>Implement a local-journal substrate backend with restart recovery, filtered queries, and health reporting.</description>
<acceptance_criteria>
- Deposits append durably to a journal file.
- Reopening the backend recovers prior deposits.
- Operators can query by threat class and recency window without changing detector code.
</acceptance_criteria>
</task>

<task number="3" type="auto">
<description>Enforce durable substrate readiness in live-response mode and cover the behavior with tests.</description>
<acceptance_criteria>
- Runtime rejects live-response use when durability is required but the backend is ephemeral or unavailable.
- A durable journal backend satisfies the readiness requirement.
- Targeted crate tests pass.
</acceptance_criteria>
</task>
</tasks>

<verification>
- cargo test -p swarm-core -p swarm-pheromone -p swarm-whisker -p swarm-runtime
</verification>

<success_criteria>
- Durable substrate selection is config-driven.
- Restart recovery works for the selected durable backend.
- Live-response durability requirements are enforced programmatically.
</success_criteria>
