# Phase 21 Plan 01: Bounded Canary Execution And Metrics

<objective>
Run a candidate detector in a bounded live lane, compare it against the production baseline, and persist current canary metrics without widening live escalation semantics.
</objective>

<read_first>
- .planning/phases/21-bounded-canary-execution-and-metrics/21-CONTEXT.md

- crates/swarm-runtime/src/service.rs
- crates/swarm-runtime/src/pipeline.rs
- crates/swarm-whisker/src/detector.rs
</read_first>

<tasks>
<task number="1" type="auto">
<description>Add canary event ingestion and detector-comparison metrics.</description>
<acceptance_criteria>
- One canary run can ingest `TelemetryEvent` inputs.
- Baseline and candidate detectors are evaluated against the same event.
- Metrics capture detections, conservative false-positive proxy, latency, and resource volume.
</acceptance_criteria>
</task>

<task number="2" type="auto">
<description>Keep candidate outputs isolated from fleet-wide escalation semantics.</description>
<acceptance_criteria>
- Candidate findings remain in canary-specific artifacts only.
- Canary execution does not deposit into the production substrate or mutate production detector assignment.
- Tests demonstrate that candidate-only detections do not alter production state.
</acceptance_criteria>
</task>

<task number="3" type="auto">
<description>Expose active canary metrics through `swarmctl` and document the workflow.</description>
<acceptance_criteria>
- `swarmctl` can ingest a canary event and reload the updated canary run.
- Human-readable and JSON output show current canary metrics.
- Docs explain the bounded canary metrics surface.
</acceptance_criteria>
</task>
</tasks>
