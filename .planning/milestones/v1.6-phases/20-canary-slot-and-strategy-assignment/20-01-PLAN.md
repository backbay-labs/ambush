# Phase 20 Plan 01: Canary Slot And Strategy Assignment

<objective>
Define the bounded canary slot contract, load candidate detector assignments from repo-owned artifacts, and persist stable canary run records.
</objective>

<read_first>
- .planning/phases/20-canary-slot-and-strategy-assignment/20-CONTEXT.md

- crates/swarm-runtime/src/replay.rs
- crates/swarm-core/src/config.rs
- docs/EVOLUTION.md
</read_first>

<tasks>
<task number="1" type="auto">
<description>Add repo-owned canary configuration and validation.</description>
<acceptance_criteria>
- `SwarmConfig` grows a typed canary section with safe defaults.
- Default ruleset includes explicit canary settings.
- Invalid canary settings fail config validation.
</acceptance_criteria>
</task>

<task number="2" type="auto">
<description>Add runtime-side canary assignment types and a persisted canary run store.</description>
<acceptance_criteria>
- Canary runs have stable IDs and slot IDs.
- Starting a canary records the baseline strategy and candidate strategy without mutating production config.
- Verification and shadow artifacts are linked into the canary run record.
</acceptance_criteria>
</task>

<task number="3" type="auto">
<description>Expose canary assignment through `swarmctl` and document the contract.</description>
<acceptance_criteria>
- `swarmctl` can start a canary from an experiment plus verification/shadow IDs.
- `swarmctl` can load a canary run by stable ID.
- Docs explain how canary config and assignment work.
</acceptance_criteria>
</task>
</tasks>

<verification>
- cargo test -p swarm-runtime canary --quiet

- cargo clippy --workspace -- -D warnings
</verification>

<success_criteria>
- The repo has a stable, reloadable canary slot contract.
- Candidate detectors can be admitted into the bounded canary lane without replacing production.
- Phase 21 can start processing live telemetry through the candidate detector.
</success_criteria>
