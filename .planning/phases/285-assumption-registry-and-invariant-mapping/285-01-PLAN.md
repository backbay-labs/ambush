# Phase 285 — Assumption Registry And Invariant Mapping

**Status:** implementation plan, 2026-09-07. Executed with the subagent-driven-development skill.
Branch `feat/assurance-285` off `main` `4046d7586` (v1.80 Red Swarm milestone complete; Phase 284
"test isolation" complete 2026-08-11, so this phase's dependency is met). This is the v1.79
Assurance-Foundation floor, run now that the ahead-of-milestone red-swarm work is done.

**Goal (ROADMAP.md).** Convert "fail-closed" from a README assertion into an AUDITABLE table
linking each fail-closed invariant to the exact function enforcing it and the assumption beneath
it, with a *broken variant* per invariant proving each check actually fires (the positive suite is
not vacuous). Two CI gates keep the table and the negative registry from rotting.

**Requirements, verbatim (REQUIREMENTS.md:827–838).**
- **MAPPING-01**: `docs/assurance/assumptions.toml` names at least 8 assumptions (ASSUME-OS-CLOCK,
  ASSUME-JETSTREAM-DURABILITY, ASSUME-KEYSTORE-ATOMICITY, ASSUME-ED25519, ASSUME-SHA256,
  ASSUME-CANONICAL-JSON, ASSUME-NETWORK-TRANSPORT, ASSUME-SUBPROCESS-ISOLATION), each with an owner
  and its dependent invariants.
- **MAPPING-02**: `docs/assurance/MAPPING.md` carries one row per fail-closed invariant, covering
  `swarm-policy`'s gates, `SwarmRuntime::authorize_and_execute`, `swarm-spine`'s envelope signing
  and chain verification, and `swarm-response`'s dispatch, each naming an exact
  `crate::module::function` path and an assumption ID.
- **MAPPING-03**: A `// INVARIANT: <Name>` source-marker convention annotates every Rust call site
  named in MAPPING.md.
- **MAPPING-04**: the mapping gate fails the build when a marker has no MAPPING.md row, or a
  MAPPING.md row names a Rust path that no longer exists.
- **MAPPING-05**: the mapping gate runs as a required step in `.github/workflows/ci.yml`.
- **FALSIFY-01**: `docs/assurance/negative-registry.toml` maps each MAPPING.md invariant to a
  `crates/*/tests/negative_*.rs` test and the production function it targets.
- **FALSIFY-02**: each registered test constructs a deliberately-broken variant of the enforcing
  function and asserts the broken variant PERMITS what the real function DENIES — proving the
  positive suite is not vacuous.
- **FALSIFY-03**: the negative-registry gate fails if any MAPPING.md row lacks a registry entry or
  names an absent test.
- **FALSIFY-04**: the negative-registry gate is a required CI step.

**Success criteria (ROADMAP.md).** (1) `assumptions.toml` parses, ≥8 assumptions each with an owner
+ dependent invariants. (2) `MAPPING.md` ≥12 invariant rows spanning `swarm-policy`, `swarm-response`,
`swarm-runtime`, `swarm-spine`, each naming an existing `crate::module::function`. (3) the mapping
gate is a required CI step and demonstrably fails against a deliberately-unmapped `// INVARIANT:`
marker. (4) every MAPPING.md row has a `negative_*.rs` test asserting a broken variant permits what
the real denies; the negative-registry gate fails on any missing entry.

**Design of record (controller rulings, 2026-09-07).**
- **The two gates live in `tools/`, not `scripts/`** — the requirement text names `scripts/check-*.sh`,
  but every gate in this repo is `tools/check-*.sh` and `tools/check-gates-wired.sh` scans `tools/`;
  a gate in `scripts/` would be unenforced by the wiring gate. Ruling: `tools/check-mapping.sh` and
  `tools/check-negative-registry.sh`; note the path slip (same as ARMSCI-02, phase 291). Wire BOTH
  into `ci.yml` in the task that adds them (`check-gates-wired.sh` fails otherwise).
- **"Fail-closed invariant"** = a source point where malformed/weak/unauthorized input is DENIED
  (not defaulted-open). Seeds for MAPPING.md (T1 inventories the full ≥12 against the real tree):
  `swarm-policy` `configurable_gate` + `PolicyVerdict::{deny, deny_with_rule, RequireHuman}`
  (`crates/swarm-policy/src/lib.rs`); `SwarmRuntime::authorize_and_execute` + the `RequireHuman`
  live-response branch (`crates/swarm-runtime/src/lib.rs:~993`); `swarm-spine` envelope signing +
  hash-chain verification; `swarm-response` dispatch's authorization/mode checks. Each row names an
  assumption ID from `assumptions.toml`.
- **The negative test is a BROKEN VARIANT, not a mutation of production.** Each `negative_*.rs`
  builds a local broken copy (or injects a permissive parameter) of the enforcing logic and asserts
  it PERMITS the exact input the real function DENIES — so a test lives beside, never edits, the real
  function. No production code changes for FALSIFY (it is a test + registry + gate phase).

### Task 1: The assumption registry and the invariant map (MAPPING-01, MAPPING-02)

**Files.** `docs/assurance/assumptions.toml` (new), `docs/assurance/MAPPING.md` (new).

**Behaviour.**
- `assumptions.toml`: ≥8 assumptions, the eight named IDs at minimum, each `[assume.<ID>]` with an
  `owner`, a one-line `statement` (what is assumed true of the environment/primitive), and
  `dependent_invariants` (the MAPPING.md invariant names that rest on it). Parses as valid TOML.
- `MAPPING.md`: ≥12 rows, one per fail-closed invariant, spanning ALL FOUR of `swarm-policy`,
  `swarm-response`, `swarm-runtime`, `swarm-spine`. Each row: an invariant `Name`, the exact
  `crate::module::function` path that ENFORCES it (verified to exist in the tree at HEAD), the
  assumption ID it depends on, and a one-line description of what it denies. INVENTORY the real
  fail-closed points (start from the seeds in the plan's design-of-record; find the rest by reading
  each crate's deny/reject/verify/RequireHuman paths) — do not invent invariants or paths.

**Tests / verification.** `assumptions.toml` parses (a tiny `python3 -c` or a Rust test) with ≥8
entries each carrying owner + dependents; `MAPPING.md` has ≥12 rows across the four crates and every
named `crate::module::function` resolves to a real item (grep/inspect each). `cargo fmt`/`clippy`
unaffected (docs only).

### Task 2: The `// INVARIANT:` markers and the mapping gate (MAPPING-03, MAPPING-04, MAPPING-05)

**Files.** `// INVARIANT: <Name>` comments at each call site named in `MAPPING.md` (comment-only
edits to the enforcing source files); `tools/check-mapping.sh` (new); a `run:` step in
`.github/workflows/ci.yml`.

**Behaviour.**
- Add a `// INVARIANT: <Name>` comment immediately at each Rust call site MAPPING.md names (the
  marker Name matches the MAPPING.md row). Comments only — no logic change.
- `tools/check-mapping.sh` (`bash`, `set -euo pipefail`): FAILS if a `// INVARIANT: <Name>` marker in
  the tree has no matching `MAPPING.md` row, OR a `MAPPING.md` row names a `crate::module::function`
  path that no longer exists in the tree. Like the repo's other gates, it PLANTS a counterexample
  (an unmapped marker + a stale path) in a temp copy and asserts it catches both before scanning for
  real (not vacuous). Wire it into `ci.yml`.

**Tests / verification.** SC3: the gate exits 0 on the real tree, and exits non-zero against a
deliberately-unmapped `// INVARIANT: <Name>` marker (prove it) AND against a MAPPING.md row whose
path was renamed away. `bash tools/check-mapping.sh` and `bash tools/check-gates-wired.sh` pass.
`cargo build`/`clippy` unaffected by the comment markers.

### Task 3: The negative-falsifiability registry, tests, and gate (FALSIFY-01..04)

**Files.** `docs/assurance/negative-registry.toml` (new); one `crates/<crate>/tests/negative_<name>.rs`
per MAPPING.md invariant; `tools/check-negative-registry.sh` (new); a `run:` step in `ci.yml`.

**Behaviour.**
- `negative-registry.toml`: one entry per MAPPING.md invariant → its `negative_*.rs` test file, the
  test fn name, and the production `crate::module::function` it targets.
- Each `negative_*.rs` builds a DELIBERATELY-BROKEN variant of the enforcing logic (a local
  permissive copy, or the real function called with a bypass/weakened parameter) and asserts the
  broken variant PERMITS the exact input the REAL function DENIES — proving the positive suite is not
  vacuous. It touches no production code. (Where a broken variant is impractical for an invariant,
  record the deviation and the closest honest falsification in the report.)
- `tools/check-negative-registry.sh`: FAILS if any MAPPING.md row lacks a registry entry, or the
  registry names an absent test file/fn. Counterexample-planted (not vacuous). Wire it into `ci.yml`.

**Tests / verification.** SC4: every MAPPING.md row has a registry entry + a passing `negative_*.rs`;
`bash tools/check-negative-registry.sh` exits 0 on the real tree and non-zero against a MAPPING.md
row with no registry entry (prove it). `cargo test -p <crate> negative_` runs the negative tests
green. `bash tools/check-gates-wired.sh` passes (both new gates wired). fmt/clippy clean.
