# Phase 297 — Kill-Chain Reconstruction

**Status:** implementation plan, 2026-09-08. Executed with subagent-driven-development. Branch
`feat/chain-297` off `main` `509e06e03` (Phase 296 complete). Second phase of v1.82. Depends on 296
(the provenance graph + `provenance_paths` traversal), which is met.

**Goal (ROADMAP.md).** Turn ephemeral sequence detections into durable graph evidence and reconstruct
multi-stage kill chains that span hunts, producing operator-auditable narratives.

**Requirements, verbatim (REQUIREMENTS.md:956–959).**
- **CHAIN-01**: `chain_reconstruction.rs` walks causal, temporal, and semantic edges and maps observed
  paths onto the stage ordering in `sequences/kill-chain-v1.yaml`.
- **CHAIN-02**: `KillChainSequenceDetector` matches are written into the graph as semantic
  kill-chain-stage edges, making ephemeral detections durable evidence.
- **CHAIN-03**: Incidents referencing disjoint `hunt_id`s connected by a causal path emit a
  `ReconstructedKillChain` persisted alongside `IncidentRecord`.
- **CHAIN-04**: `narrate()` produces a stage-by-stage narrative, tested against at least two existing
  multi-stage fixtures with stage order matching each fixture's declared chain.

**Success criteria (ROADMAP.md).** (1) all sequence-detector matches written as semantic
kill-chain-stage edges (new integration test); (2) ≥2 existing multi-stage fixtures reconstruct with
stage order exactly matching each fixture's declared chain; (3) narration produces a non-empty
stage-by-stage string for every reconstructed chain; (4) two investigations from different hunts
sharing a causal path reconstruct into ONE chain, not two disjoint incidents.

## Design of record (controller rulings, 2026-09-08; re-verify at HEAD)

- **Reuse the existing `SemanticRelation::KillChainStage` edge (CHAIN-02).** The graph already models
  KillChainStage semantic edges (for attack techniques). CHAIN-02 = also write `KillChainSequenceDetector`
  matches as `KillChainStage` semantic edges, so a detected sequence becomes durable graph evidence
  (the ephemeral match survives in the persisted snapshot). Wire this where sequence-detector matches
  are observed in the runtime (read the detect path from `sequence_detector.rs` through the service);
  the edge must carry the rule's stage + technique so CHAIN-01 can map it. Preserve the existing
  attack-technique KillChainStage emission unchanged.
- **`chain_reconstruction.rs` is a new read-only module (CHAIN-01), in `swarm-runtime`.** It takes a
  `KnowledgeGraphSnapshot` (+ the loaded kill-chain-v1.yaml rules) and, using the Phase 296
  `provenance_paths`/edge traversal, walks causal+temporal+semantic edges to find observed technique/
  stage paths, then maps each onto a rule's `attack_chain` stage ordering — returning the matched stage
  sequence. It does NOT mutate the graph. It sits alongside `sphinx_agent`/`correlation` (both in
  swarm-runtime), reading the snapshot the same way `CorrelationEngine::graph_provenance_link` does.
- **`ReconstructedKillChain` is a new persisted type (CHAIN-03), alongside `IncidentRecord` in
  swarm-spine.** When two incidents referencing DISJOINT `hunt_id`s are connected by a causal path in
  the graph, reconstruction emits one `ReconstructedKillChain` (its stages, the hunts it spans, the
  causal path) persisted next to the `IncidentRecord` (extend `IncidentStore`/the record, or a sibling
  store method — follow the existing persistence shape; do not break the existing incident persistence
  or its tests). SC4: two different-hunt investigations sharing a causal path become ONE chain, not two
  disjoint incidents — an integration test proves it.
- **`narrate()` (CHAIN-04)** produces a non-empty stage-by-stage human-readable narrative from a
  `ReconstructedKillChain` (stage order = the reconstructed order). Tested against ≥2 existing
  multi-stage fixtures (kill-chain-v1.yaml rules), asserting the narrated stage order EXACTLY matches
  each fixture's declared `attack_chain` stage sequence.
- **Producer-wiring note (from 296).** The Phase 296 raw-telemetry causal edges (FileWrite/etc.,
  pid-keyed) do not fire on current telemetry, but CHAIN-01 walks causal+temporal+semantic edges and
  the EXISTING causal (`ProcessParentChild`/`NetworkFlowOrigin`) + semantic (`KillChainStage`) +
  temporal edges DO fire — so reconstruction has real edges to walk without any producer change. If a
  fixture's reconstruction needs an edge that only the 296 raw relations would provide, note it; do NOT
  expand scope into telemetry-normalization producer-wiring in this phase unless a CHAIN requirement
  cannot otherwise be met (surface it as a ruling if so).
