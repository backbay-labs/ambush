  <behavior>
    - The detector only evaluates `TelemetryPayload::NetworkConnect`
    - Empty `process_name` or `destination_ip` produce no finding
    - Suspicious destination ports produce a medium-confidence finding
    - Process-to-port mismatches produce a medium-confidence finding when a per-process allowlist exists and the destination port is outside it
    - Periodic low-jitter repeated connections to the same destination tuple produce a high-confidence beaconing finding
    - Multiple heuristics on one event still produce a single `DetectionFinding`
  </behavior>
  <action>
    1. Create `crates/swarm-whisker/src/network_connect.rs` containing:
       - `NetworkConnectProfile` with:
         - `suspicious_ports: Vec<u16>`
         - `process_port_allowlist: HashMap<String, Vec<u16>>`
         - `beacon_min_sample_count: usize`
         - `beacon_window_ms: i64`
         - `beacon_min_interval_ms: i64`
         - `beacon_max_jitter_ratio: f64`
         - `high_confidence_threshold: f64`
         - `medium_confidence_threshold: f64`
       - A `Default` implementation using:
         - a small built-in suspicious-port set for classic C2/backdoor ports (keep it intentionally narrow)
         - empty `process_port_allowlist`
         - beacon defaults from research: `4`, `900_000`, `15_000`, `0.20`
       - `NetworkConnectProfile::validate()` enforcing:
         - `beacon_min_sample_count >= 3`
         - `beacon_window_ms > 0`
         - `beacon_min_interval_ms > 0`
         - `0.0 < beacon_max_jitter_ratio <= 1.0`
         - `beacon_window_ms >= beacon_min_interval_ms * (beacon_min_sample_count - 1)`
         - no empty process names in `process_port_allowlist`
         - `validate_confidence_thresholds()`

    2. Implement `NetworkConnectDetector`:
       - Store normalized `suspicious_ports`
       - Store normalized `process_port_allowlist` keys in lowercase with deduped ports
       - Track beacon timestamps with `Arc<Mutex<HashMap<BeaconKey, VecDeque<i64>>>>`
       - Use a private `BeaconKey` containing:
         - `host_id` when present, else `event.source`
         - normalized `process_name`
         - normalized `destination_ip`
         - `destination_port`
         - normalized `protocol`
       - Normalize timestamps to milliseconds using the same seconds-vs-ms guard used by existing stateful detectors
       - Trim old entries older than `beacon_window_ms` before appending the new timestamp

    3. Implement one-event evaluation:
       - Normalize `process_name`, `destination_ip`, and `protocol`
       - Evaluate `suspicious_port`
       - Evaluate `process_port_mismatch`
       - Evaluate beaconing using consecutive inter-arrival intervals, mean interval, and coefficient of variation / jitter ratio
       - Emit no finding if none of the heuristics fire
       - Emit exactly one `DetectionFinding` otherwise with:
         - `threat_class: ThreatClass::CommandAndControl`
         - `strategy_id: "network_connect"`
         - `severity/confidence` mapping:
           - port anomaly only => `Severity::Medium` + `medium_confidence_threshold`
           - process-port mismatch only => `Severity::Medium` + `medium_confidence_threshold`
           - beaconing (alone or combined) => `Severity::High` + `high_confidence_threshold`
       - Evidence must include:
         - `process_name`, `destination_ip`, `destination_port`, `protocol`, `host_id`
         - `heuristics.beaconing`, `heuristics.suspicious_port`, `heuristics.process_port_mismatch`
         - beacon stats when beaconing fires (`sample_count`, `intervals_ms`, `mean_interval_ms`, `jitter_ratio`)
         - allowlist context when a process allowlist exists

    4. Keep detector behavior deliberately local:
       - do not add async code
       - do not call into `PheromoneSubstrate`
       - do not emit multiple findings for one event
  </action>
