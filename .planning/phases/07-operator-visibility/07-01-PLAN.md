# Phase 7 Plan 01: Operator Visibility

<objective>
Turn the durable runtime into something operators can inspect through one serializable status report with stage metrics and recent-decision correlation.
</objective>

<read_first>
- .planning/phases/07-operator-visibility/07-CONTEXT.md
- crates/swarm-runtime/src/lib.rs
- crates/swarm-runtime/src/service.rs
- crates/swarm-spine/src/store.rs
</read_first>

<tasks>
<task number="1" type="auto">
<description>Add stage-aware runtime metrics for detect, policy, persist, and response execution.</description>
<acceptance_criteria>
- Metrics record success/failure counters per stage.
- Metrics expose bounded latency distribution buckets.
- Metrics are available as a serializable snapshot.
</acceptance_criteria>
</task>

<task number="2" type="auto">
<description>Build one operator status report covering runtime mode, component readiness, and recent decisions.</description>
<acceptance_criteria>
- Status report covers detector, substrate, policy, response, and replay store components.
- Report includes recent persisted decisions and stable identifiers.
- Warning conditions reflect degraded durability or readiness.
</acceptance_criteria>
</task>

<task number="3" type="auto">
<description>Add tests that prove metrics and operator status are populated through real runtime execution.</description>
<acceptance_criteria>
- Runtime execution populates detect/policy/persist/response metrics.
- Operator status can be built after persisted execution.
- Targeted runtime tests pass.
</acceptance_criteria>
</task>
</tasks>

<verification>
- cargo test -p swarm-runtime -p swarm-spine
</verification>

<success_criteria>
- Operator status is one serializable surface.
- Stage metrics are populated through real execution paths.
- Recent decisions correlate stable identifiers across the durable runtime.
</success_criteria>
