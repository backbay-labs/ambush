# Phase 290 — Bidirectional Co-Evolution And Convergence

**Status:** implementation plan, 2026-09-07. Executed with the subagent-driven-development skill.
Branch `feat/red-swarm-290` off `main` `4d1f476cf` (phases 288 + 289 landed).

**Goal (ROADMAP.md).** Make both sides *actually move*, measured against **real detector runs**
rather than 289's self-play snapshot, and guarantee every campaign terminates. Phase 288 plans,
289 scores/bounds/remembers against a *static* `EvasionCoverageSnapshot`; 290 closes the loop:
each generation red plans (biased by what evaded last time), the plan is materialized to telemetry
and run through the real detector pipeline for the *actual* catch, blue adapts by closing the gaps
red just exploited, and a bounded stopping rule ends the campaign.

**Requirements, verbatim (REQUIREMENTS.md:883–886).**
- **COEVOLVE-01**: `RedSwarmCampaign::run` plans, materializes events, runs them through the real
  detector pipeline, records outcomes, and computes both red fitness and blue catch rate per gen.
- **COEVOLVE-02**: a bounded stopping rule terminates every run on `max_generations`, fitness
  plateau within `convergence.min_delta` for `convergence.patience` generations, or full blue
  coverage; `stop_reason` is recorded.
- **COEVOLVE-03**: `GenomeRedSwarm` implements the existing `RedSwarmAdapter` trait alongside
  `SuiteRedSwarmAdapter`.
- **COEVOLVE-04**: `EvolutionAdversarialSummary.corpus_sequence_id` may reference a campaign
  generation without changing its public shape; campaign reports persist under
  `data/red-swarm/campaigns/`.

**Success criteria (ROADMAP.md).**
1. A campaign configured for 6 generations never executes a 7th, for a fixed seed.
2. A campaign whose fitness plateaus stops early with `stop_reason == "plateau"`.
3. Over at least 4 generations, blue catch rate is non-decreasing on average and red technique
   weights measurably shift away from generation-zero favourites once recorded as caught.
4. Two invocations at the same seed produce byte-identical campaign reports except a generated-at
   timestamp.

**Design of record (controller ruling, 2026-09-07 — see `scratchpad/290-design-notes.md`).**
Both sides move, measured by real detector runs:
- **Red moves** by biasing `RedGenome::plan` with a per-technique weight map derived from
  `AttackPatternDb::technique_success_rate` (down-weight caught techniques). The weight is an
  OPTIONAL deterministic input; `None`/empty reproduces 288 byte-for-byte.
- **Blue moves** by greedy gap-closing: its state is the enabled `DetectionConfig.strategies`;
  each generation, after running the enabled detectors over red's corpus, blue enables the
  strategies that would have caught the techniques that evaded (from the evasion catalog's
  detector→technique mapping). Catch rate is therefore **non-decreasing** (coverage only grows),
  bounded (finite strategies → converges to full coverage, a COEVOLVE-02 stop), and honest
  (real detector runs reveal the gaps). This uses the detector pipeline, NOT the heavy
  file-based `mutation/` harness (its `now_ms` would break SC4; no requirement names it).
- Determinism: the whole loop is seeded; the ONLY clock read is the report's `generated_at_ms`
  (the SC4-exempt field). No entropy, no response authority — the 288/289 invariants still bind.

**What exists (verified in tree at `4d1f476cf`).**
- `red_swarm/`: `RedGenome::plan(seed, generation, &CampaignParams, &TargetGraph) -> Result<RedPlan>`
  (288, pure); `AttackScorer`, `StealthBudget`/`BudgetOutcome`, `AttackPatternDb`/`AttackPatternRecord`
  (289); the `RedSwarmAdapter` trait + `SuiteRedSwarmAdapter` (re-stamps suite events with new
  ids/hosts/timestamps) + `MockRedSwarm`; `AdversarialSequenceArtifact`; `RedSwarmError`.
- `detector_factory::build_detector_from_strategy(strategy, &DetectionConfig) -> Result<RuntimeDetector, DetectorFactoryError>`;
  `RuntimeDetector: DetectionStrategy`; `DetectionStrategy::evaluate(&self, &TelemetryEvent) -> Vec<DetectionFinding>`.
  `evasion_coverage` already runs detectors over scenario events (`evaluate_repo_evasion_coverage`)
  and loads the catalog (`EvasionTechniqueCatalogDetector { detector, intentionally_uncovered, .. }`,
  per-technique `mapped_detectors: Vec<String>`) — reuse both. `now_ms()` there feeds only
  `generated_at_ms`, never the detection logic.
- `swarm_core::config::detection::DetectionConfig { strategies: Vec<String>, .. }` — blue's state.
- `evolution_status::EvolutionAdversarialSummary { corpus_sequence_id: Option<String>, .. }` — the
  field already exists (maps from `adversarial_corpus_sequence_id`); COEVOLVE-04 wires the campaign
  generation id in without changing the struct's shape.
- CLI: `swarmctl red-swarm {plan, score}` in `crates/swarm-cli/src/red_swarm_cmd.rs`.

## Global constraints

Carried from 288/289 (still bind): Rust 1.97.1, edition 2024; `cargo fmt --all`; `cargo clippy
--workspace --all-targets -- -D warnings`; `unwrap_used`/`expect_used` denied outside `mod tests`;
no `panic!`/`todo!`; `tools/check-{runtime-panic-contract,workspace-layering,visibility-baseline,gates-wired}.sh`
stay green. No new crate dependency. **The red lane never reaches response authority** — nothing new
names `execute_response`/`ResponseAdapter`/`live_response`, imports `swarm_response`, or takes a
broadcaster; `check-workspace-layering` keeps `swarm-runtime` out of the TCB. Techniques are
catalogued or they do not exist. **Determinism is a property, not a claim**: a campaign at a fixed
seed is byte-identical run to run except `generated_at_ms` (a test asserts this, stripping that one
field). No wall clock on any output path but that field. Public items documented in the crate's
voice; tests `a_thing_does_x_when_y`; commits `git commit -s`, Conventional Commits.

**Pre-flight scan (controller settles before Task 1; rulings in the ledger).**
- **Planner weight-injection is additive and back-compatible.** Extending `RedGenome::plan` (or the
  operators) to take `Option<&TechniqueWeights>` must leave the 288 byte-identical tests passing for
  `None`. Prefer a new method (`plan_weighted`) or an optional trailing arg with a `None`-preserving
  default, so 288's `plan_is_byte_identical_for_identical_arguments` is untouched.
- **Blue catch → red fitness bridge.** The per-generation detector run yields per-technique
  caught/not; assemble those into the `EvasionCoverageSnapshot` shape `AttackScorer::score` already
  consumes (or a thin equivalent), so 289's scorer is reused verbatim, not reimplemented.
- **`data/red-swarm/campaigns/` persistence is deterministic and side-effect-scoped.** Reports are
  written only by the CLI/campaign entry, never by the pure planner/scorer; the path is
  repo-relative; a test writes to a temp dir, not the repo.

### Task 1: `GenomeRedSwarm` — materialize a plan, implement `RedSwarmAdapter` (COEVOLVE-03)

**Files.** `crates/swarm-runtime/src/red_swarm/genome_adapter.rs` (new) + one `pub mod
genome_adapter;` in `red_swarm/mod.rs`. Read `SuiteRedSwarmAdapter` first and mirror its
re-stamping.

**Types & behaviour.**
- `pub struct GenomeRedSwarm { /* the graph + campaign params + optional technique weights it plans with */ }`
  implementing `RedSwarmAdapter` alongside `SuiteRedSwarmAdapter`.
- It plans a `RedPlan` (via `RedGenome::plan`, or takes one), applies the `StealthBudget`, then
  **materializes** the budgeted `GeneStep`s into an `AdversarialSequenceArtifact`: for each step,
  pull its scenario's events (by `scenario` ref + `event_indices`) and re-stamp them with new event
  ids, a host derived from `host_slot`, and a timestamp from `offset_ms` + the campaign clock —
  exactly as `SuiteRedSwarmAdapter` re-stamps, deterministically, no wall clock.
- Reuses the scenario/event loaders 288 already uses; invents no event shape (catalog-bounding).

**Tests.** `GenomeRedSwarm` implements `RedSwarmAdapter` (trait-object usable alongside
`SuiteRedSwarmAdapter`); materialization is byte-identical for identical `(seed, generation,
campaign, graph)`; every materialized event traces to a real scenario event; the artifact's event
count equals the budget's `events_emitted`.

**Verification.** `cargo fmt --all --check`; `cargo clippy -p swarm-runtime --all-targets -- -D
warnings`; `cargo test -p swarm-runtime red_swarm::genome_adapter`.

### Task 2: Technique-weighted planning + the one-generation detector run (COEVOLVE-01 part A)

**Files.** `red_swarm/genome.rs` (additive weight injection — do NOT disturb the pure `plan`);
`red_swarm/campaign.rs` (new; the single-generation primitive) + `pub mod campaign;` in `mod.rs`.

**Weight injection (the red-move).**
- `pub struct TechniqueWeights(BTreeMap<String, f64>)` (or similar) built from
  `AttackPatternDb::technique_success_rate` per graph technique.
- A `RedGenome::plan_weighted(seed, generation, &CampaignParams, &TargetGraph, Option<&TechniqueWeights>)`
  that biases operator technique selection toward higher-success techniques **deterministically**
  (weights order/scale the existing candidate choice; no entropy added). `plan` becomes
  `plan_weighted(.., None)`. 288's `plan_is_byte_identical_for_identical_arguments` and
  `no_entropy_path_exists_in_the_red_lane` MUST still pass unchanged.

**One generation (the measured run).**
- `run_generation(gen, seed, &CampaignParams, &TargetGraph, &DetectionConfig, &StealthBudget,
  Option<&TechniqueWeights>) -> GenerationOutcome` that: plans (weighted) → materializes
  (`GenomeRedSwarm`) → builds the enabled detectors (`build_detector_from_strategy`) → runs
  `DetectionStrategy::evaluate` over the corpus → maps findings to per-technique caught/not →
  produces `AttackPatternRecord`s, the blue **catch rate**, and the **red fitness** (assemble the
  per-technique catch into the snapshot shape and call `AttackScorer::score`).
- `GenerationOutcome { generation, red_fitness: AttackFitness, blue_catch_rate: f64, records:
  Vec<AttackPatternRecord>, evaded_techniques: Vec<String> }`. Deterministic (no clock).

**Tests.** Weighted planning shifts selection toward a high-weight technique and is byte-identical
per seed; `plan_weighted(.., None)` == `plan`; `run_generation` on a fixture graph+config yields a
catch rate in `[0,1]`, records one entry per (technique, detector) evaluated, and a red fitness
consistent with the catch (fully-caught corpus → `red_fitness == 0.0`).

**Verification.** As Task 1, plus `cargo test -p swarm-runtime red_swarm::campaign red_swarm::genome`.

### Task 3: `RedSwarmCampaign::run` — the bidirectional loop + bounded stopping rule (COEVOLVE-01 part B, COEVOLVE-02)

**Files.** `red_swarm/campaign.rs` (extend).

**Types & behaviour.**
- `pub struct CampaignConfig { max_generations: u32, convergence: Convergence { min_delta: f64,
  patience: u32 }, seed, campaign params, initial DetectionConfig, StealthBudget }`.
- `RedSwarmCampaign::run(&self) -> CampaignReport`: iterate generations; each generation calls
  `run_generation` with the weights derived from the `AttackPatternDb` accumulated so far, records
  its outcome into the db, then **blue moves** — enable the `DetectionConfig.strategies` that catch
  the generation's `evaded_techniques` (from the catalog's detector→technique mapping); catch rate
  is non-decreasing by construction.
- **Stopping rule (COEVOLVE-02):** stop and record `stop_reason` when any holds — `max_generations`
  reached (`"max_generations"`); red fitness plateaus within `convergence.min_delta` for
  `convergence.patience` generations (`"plateau"`); blue reaches full coverage of the reachable
  technique set (`"full_coverage"`). Every path terminates.

**Tests.** SC1: a 6-generation config runs exactly 6, never a 7th, at a fixed seed. SC2: a config
whose fitness is flat stops with `stop_reason == "plateau"` before `max_generations`. SC3: over ≥4
generations, `blue_catch_rate` is non-decreasing on average AND a technique caught in gen 0 has a
strictly lower selection weight by the last generation (assert the weight shift on a constructed
graph where gen-0 favourites get caught). Full-coverage stop fires when blue covers everything
reachable.

**Verification.** As above, plus the four `tools/check-*.sh` gates.
