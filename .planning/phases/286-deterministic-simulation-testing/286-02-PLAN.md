## Required behavior

A live effect requires a durable, immutable reservation recording the exact
request identity, request content and authorization intent before dispatch. A
completion receipt records an observed result after the effect. These are two
different records: an intent never asserts successful completion. An interrupted
or ambiguous effect remains unresolved; retry must never duplicate it. This is
at-most-once execution with explicit uncertainty, not guaranteed exactly-once
completion or automatic rollback.

The dispatch journal is a local unsigned record protected by the OS and
filesystem. It is not an Ed25519-signed audit receipt. Existing signed audit and
substrate evidence retain their own verification paths. Completion publication
can fail after an effect; the durable intent must still prevent a second effect.

The policy decision remains authoritative on every live entry: `Deny`, unapproved
`RequireHuman`, malformed input, invalid/expired lease and journal refusal produce
zero effects, including when the future is cancelled before it returns.

## Tasks and acceptance evidence

### Task 1: Own durable request identity at the store boundary

- [ ] Implement a bounded append-only journal with fsynced reservation records,
  exclusive writer ownership, safe reopen, and fail-closed handling of malformed,
  truncated, conflicting or otherwise untrusted persisted records.
- [ ] Atomically reserve an immutable identity-to-request binding before any live
  effect; concurrent attempts, changed-content reuse and restarted callers cannot
  obtain a second dispatch permission. Do not evict reservations and silently
  enable reuse when capacity is exhausted.
- [ ] Preserve unresolved reservations across reopen. A persisted intent or an
  ambiguous outcome cannot be automatically retried. Document the availability
  cost: capacity exhaustion or unrecoverable journal corruption closes dispatch.
- [ ] Prove store refusal before effects for duplicate/conflicting requests,
  capacity, corrupt/truncated input, a second writer and persistence failure;
  retain the request reservation if the outcome write fails.

### Task 2: Enforce the journal on both production runtime entry paths

- [ ] Require the same reservation protocol in `SwarmRuntime::authorize_and_execute`
  and `audit_authorize_and_execute_instrumented_internal`, covering its public
  audit and human-approved wrappers. A test-only wrapper is insufficient.
- [ ] Bind the record to the request and the successful policy/lease/guard path;
  flush it before calling an effectful response adapter. Persist completion only
  after observing a result; return explicit uncertainty/failure when persistence
  fails without repeating dispatch.
- [ ] Disable internal retries of effectful adapter calls whose first outcome may
  be ambiguous. An idempotency reservation outside a retrying adapter does not
  prevent multiple effects inside that adapter.
- [ ] Prove both entry paths reject a live effect without a durable store and
  refuse duplicate delivery, denial, human-gate and invalid-lease cases.

### Task 3: Bind production composition and reload to the same store

- [ ] Open the durable dispatch journal under the configured audit directory in
  real ingest/service composition. Startup/open failure closes live response.
- [ ] Share the same `Arc` across runtime handles and policy reload; do not replace
  it with an empty journal when constructing a new runtime handle.
- [ ] Prove a real composed runtime can dispatch once, reload/reopen, and refuse
  the same request without a second effect. Prove missing/unusable durable
  storage cannot silently select a live-response memory fallback.

### Task 4: Rewrite DST around real effects and persistent recovery

- [ ] Drive the real runtime, gate, sandbox effect adapter and persistent
  local-journal pheromone substrate. Use independent effect observations, not
  only counters in a harness-owned adapter.
- [ ] Inject cancellation before effect, cancellation after effect but before
  completion publication, and actual persistent-substrate close/reopen between
  policy allowance and publication. Restart and redeliver the same request.
- [ ] Derive varied schedules and request/policy combinations from the seed;
  measure effective schedule diversity so 5,000 seeds cannot mean four repeated

  schedules rather than treating a seed label as additional coverage.
- [ ] Ordering oracle: every observed effect has a matching durable prior intent

  observed outcomes. Read persisted records independently of in-memory state.
- [ ] Disposition oracle: forbidden effects fail even when cancellation leaves
  no returned outcome. `Deny` and unapproved `RequireHuman` produce zero effects.
- [ ] At-most-once oracle: each immutable request identity has at most one effect

- [ ] Preserve exact `SWARM_DST_SEED=<n>` replay and report the seed, generated

## Evidence boundary and continuation

Required evidence covers a single host/process recovery model and one logical
local persistent substrate reopened over the same storage. It does not establish
distributed JetStream failover, multi-node exactly-once effects, immunity to
privileged filesystem tampering, or power-loss behavior beyond the filesystem's
fsync contract. Future-drop tests model cancellation; actual child-process death
must be separately demonstrated before claiming process-kill coverage.
