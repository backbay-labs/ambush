# Phase 286 — Deterministic Simulation Testing

**Status:** implementation plan, 2026-09-07. Executed with the subagent-driven-development skill.
Branch `feat/dst-286` off `main` `5ad9b6850` (Phase 285 "assumption registry + invariant mapping"
complete and merged, so this phase's dependency is met). This is the second v1.79
Assurance-Foundation phase: 285 made fail-closed *auditable*; 286 makes receipt-before-action and
no-double-dispatch *survive adversarial scheduling and mid-operation crashes*, not only the happy
path.

**Goal (ROADMAP.md).** Prove receipt-before-action ordering and no-double-dispatch hold under
adversarial scheduling and mid-operation crashes. A seeded, deterministic-simulation harness drives
the REAL `SwarmRuntime`, a REAL approval gate, and the REAL pheromone substrate — no mocks —
injecting faults at the exact points a crash could split an action from its receipt, and asserting
three oracles over every seed. A failing seed is named and one-command reproducible.

**Requirements, verbatim (REQUIREMENTS.md:842–847).**
- **DST-01**: `crates/swarm-runtime/tests/dst_fault_injection.rs` drives the real
  `SwarmRuntime::authorize_and_execute` (`crates/swarm-runtime/src/lib.rs:753`), a real approval
  gate, and the real pheromone substrate, with no mocks.
- **DST-02**: Seeded fault injection covers dropping the future mid-poll before dispatch, dropping it
  after dispatch but before receipt persistence, and closing/reopening the substrate between
  policy-allow and receipt-persist.
- **DST-03**: Three oracles assert receipt-before-action ordering, exact disposition against the
  deterministic policy verdict, and no double-dispatch per request.
- **DST-04**: A 64-seed corpus runs on every PR; a >=5,000-seed corpus runs in
  `.github/workflows/dst-nightly.yml`.
- **DST-05**: `SWARM_DST_SEED=<n>` replays one episode's exact fault plan for one-command
  reproduction.
- **DST-06**: `docs/assurance/MAPPING.md` gains a harness section stating the evidence boundary:
  single-process, single-substrate-instance, not distributed JetStream failover.

**Success criteria (ROADMAP.md).** (1) the harness drives the real `authorize_and_execute`, a real
approval gate, and the real substrate, no mocks; (2) at least three fault classes are injected:
future-drop before dispatch, future-drop after dispatch but before receipt persistence, and
substrate close/reopen between policy-allow and receipt-persist; (3) a 64-seed corpus on every PR
and a 5,000-seed corpus nightly, naming the failing seed on any oracle violation; (4)
`SWARM_DST_SEED=<n>` reproduces one episode's exact fault plan, and MAPPING.md states the evidence
boundary as single-process and single-substrate-instance.

## Design of record (controller rulings, 2026-09-07)

These were settled by reading the real runtime at HEAD (`5ad9b6850`); they bind the tasks.

- **DST-01's line ref (`lib.rs:753`) is STALE.** `SwarmRuntime::authorize_and_execute` is at
  `crates/swarm-runtime/src/lib.rs:972` at HEAD (an `async fn` returning
  `Result<ResponseReceipt, RuntimeError>`). The harness targets the method **by name**, never by
  line. Record the slip; do not edit the requirement text (same convention as the 285/291 path
  slips).

- **The real execution sequence, and the three fault points.** `authorize_and_execute` (`:972`):
  `policy.evaluate` → verdict match (Deny / RequireHuman-in-LiveResponse both `Err`) →
  `evaluate_guard_rejection` → `prepare_containment` → `policy.issue_lease` → `ensure_active_lease`
  → **`self.response.execute(request, &lease, mode).await`** (this is the DISPATCH — the action) →
  `decorate_receipt_with_governance` → `record_containment_lease` → returns the `ResponseReceipt`.
  It does **not** itself persist the receipt to the substrate — the substrate persist lives in the
  audit caller (`audit_authorize_and_execute` / `_instrumented_internal`, `:1057`/`:1124`), which
  drives the same execution and then deposits. So the harness's unit of work — the **episode** — is
  the composition *allow → dispatch → receipt-persist*, and the three DST-02 fault points map onto
  it as: (a) before `response.execute` returns (before dispatch); (b) after `response.execute`
  returns but before the substrate deposit (after dispatch, before receipt persist); (c) substrate
  close/reopen anywhere in the allow→persist window.
  **T1 ruling to confirm-in-code:** whether to drive `audit_authorize_and_execute` (which already
  composes dispatch + persist) or `authorize_and_execute` + an explicit real substrate deposit. T1
  picks the one that keeps the persist a REAL substrate write and exposes all three fault points;
  DST-01 is satisfied either way because `authorize_and_execute` is the method under test inside it.

- **The fault-injection mechanism (THE CRUX).** A **deterministic, single-threaded executor** — a
  hand-rolled `poll` loop over the episode `Future` with a no-op `Waker`, no wall clock, no
  entropy, no `tokio` multi-thread — is the substrate for reproducibility: a seed maps to an exact
  `FaultPlan`, and polling order is fixed. Fault classes (a) and (b) are **future drops**: the
  executor polls the episode to a class-determined checkpoint, then drops the future (a crash
  simulation — no more polls). Because `authorize_and_execute` is an opaque `async fn` whose
  internal await points the harness cannot instrument, the *precision* of "before vs. after
  dispatch" is provided by the **harness's own real `ResponseAdapter`** (see next ruling), which
  yields at a controllable checkpoint around the dispatch. Fault class (c) is **not a drop**: a
  substrate seam the harness triggers to close then reopen the real substrate within the
  allow→persist window, after which the episode continues and the oracles judge the outcome.

- **The observation + fault seam is a REAL `ResponseAdapter`, not a mock (this is idiomatic here).**
  `dispatch_integration.rs` already wraps real components with `AtomicUsize` recording counters —
  observing, not mocking. The harness provides a real `ResponseAdapter` implementation that (1)
  RECORDS every `execute` call (a monotonic dispatch log: request id, order, at-most-once count) for
  the ordering and no-double-dispatch oracles, and (2) exposes an `async` checkpoint at the dispatch
  boundary so the deterministic executor can drop precisely before vs. after the action. This is a
  legitimate real adapter (the runtime is generic over its executor `E`), not a mock of the runtime,
  gate, or substrate — which stay real per DST-01. The gate is a real `StaticApprovalGate` with a
  deterministic config so every request has a known ground-truth verdict for the disposition oracle;
  the substrate is a real `InMemoryPheromoneSubstrate` (`PheromoneSubstrate`).

- **The three oracles are properties UNDER TEST, encoded against the engine's ACTUAL guarantee — not
  assumed true.** DST's job is to NAME a violating seed, not to presume correctness. T1 must first
  establish, from the real code, the exact receipt-before-action guarantee the engine provides
  (given it dispatches *then* persists, this is about completeness/recovery: no action-effect
  without a corresponding persisted receipt, and vice versa), and record it in the report. T3 then
  encodes the oracles to that ground truth: (1) **receipt-before-action** — no episode ends with the
  recording adapter showing an action took effect but the substrate holding no matching receipt (and
  the reverse); (2) **exact disposition** — the episode outcome (receipt status / error variant)
  equals what the deterministic verdict demands (Allow→executed, Deny→denied, RequireHuman-in-live→
  denied); (3) **no double-dispatch** — across an episode (including any modeled crash+retry) each
  request's action executes at most once. If the honest reading is that a given fault class
  legitimately CAN split action from receipt in the current single-process engine (no atomic
  journal), that is a real finding: record it as the evidence boundary (DST-06) rather than
  asserting a guarantee the engine does not make — the oracle then asserts the guarantee the engine
  DOES make, and the boundary names what it does not.

- **Determinism is a hard property, byte-for-byte.** Same seed → same fault plan → same episode →
  same oracle result, every run, on every machine. No `Instant::now`/`SystemTime`, no RNG entropy
  (seed a small deterministic PRNG — reuse the repo's `RedGenomeRng`/xoshiro pattern if it fits, or
  a tiny SplitMix), no `HashMap` iteration on any decision path (`BTreeMap`/`BTreeSet`), no real
  tokio timers. `SWARM_DST_SEED=<n>` (DST-05) reconstructs one seed's exact `FaultPlan` and runs
  just that episode.

- **Scripts vs. tools + CI.** No new `tools/check-*.sh` gate is required by DST (the corpus IS the
  test). DST-04's PR corpus is a `#[test]` in `dst_fault_injection.rs` that runs under the existing
  test lane on every PR; the nightly 5,000-seed corpus is a NEW workflow
  `.github/workflows/dst-nightly.yml` (a `schedule:` cron + manual `workflow_dispatch`), gated large
  so it never runs in the fast PR lane. If a `run:`-style seam is added anywhere, it is additive and
  must keep `tools/check-gates-wired.sh` green.

### Task 2: The three fault classes — future-drop before/after dispatch, substrate close/reopen (DST-02)

**Files.** `crates/swarm-runtime/tests/dst_fault_injection.rs` (extend).

**Behaviour.**
- The recording `ResponseAdapter` gains an `async` checkpoint at the dispatch boundary so the
  deterministic executor can drop the episode PRECISELY (a) before `execute`'s effect (before
  dispatch) and (b) after `execute` returns but before the substrate deposit (after dispatch, before
  receipt persist). The adapter still records every dispatch (order + at-most-once count).
- A substrate seam for class (c): close then reopen the real substrate within the allow→persist
  window, then let the episode continue.
- Wire `FaultPlan` → the executor: for a drop class, poll to the class's checkpoint then drop; for
  the close/reopen class, trigger the substrate seam at the window. Each class is selected
  deterministically by seed.

**Tests / verification.** One focused test per fault class proves it fires at the intended point:
class (a) leaves the dispatch log EMPTY (action never took effect); class (b) shows exactly one
dispatch and NO persisted receipt (the split the oracle will judge); class (c) shows the substrate
was closed/reopened in-window and the episode observed it. Determinism: same seed → same class →
same observation, twice, byte-identical. `cargo test -p swarm-runtime dst_` green (scoped),
fmt/clippy clean. No `crates/*/src/**` change (or escalate per Global Constraints).
