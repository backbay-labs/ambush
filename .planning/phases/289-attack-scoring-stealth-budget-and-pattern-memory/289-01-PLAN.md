# Phase 289 — Attack Scoring, Stealth Budget And Pattern Memory

**Status:** implementation plan, 2026-09-07. Executed with the subagent-driven-development
skill: one implementer per task, a task review after each, a whole-branch review before merge.
Branch `feat/red-swarm-289` off `main` `6c07ab402` (phase 288 landed as `034efd2f7`).

**Goal (ROADMAP.md:1194).** Phase 288 gave the red lane a pure planner that recombines
catalogued techniques into a deterministic `RedPlan`. It scores nothing and bounds nothing: a
plan can name twenty steps of the same loud technique and the engine has no opinion. Phase 289
turns a plan into a **scored, resource-bounded** object and gives each generation **memory** of
what the last one survived — so red cannot win by volume, and a later generation can bias toward
what actually evaded. All of it stays a self-play estimate against a pre-computed coverage
snapshot; Phase 290 replaces the snapshot with real detector runs.

**Requirements, verbatim (REQUIREMENTS.md:876–879).**
- **ATKSCORE-01**: `AttackScorer` computes `AttackFitness { evasion_rate, stealth, red_fitness }`
  from an adversarial sequence and an `EvasionCoverageSnapshot`, where `evasion_rate = 1.0 -
  detector-weighted catch_rate`.
- **ATKSCORE-02**: `StealthBudget` (`max_events_per_generation`, `max_distinct_hosts`,
  `max_technique_repeats`) deterministically truncates proposed steps once exhausted, so red
  cannot win by volume.
- **ATKSCORE-03**: `AttackPatternDb` is an append-only JSON-lines store recording `{generation,
  technique, detector, detected}` with `technique_success_rate` biasing later generations.
- **ATKSCORE-04**: `swarmctl red-swarm score --json` prints `red_fitness`, `evasion_rate`,
  `stealth`, and `events_emitted`.

**Success criteria (ROADMAP.md:1200–1203).**
1. A fully caught plan scores `red_fitness == 0.0`; a plan built only from declared-uncovered
   techniques scores above `0.5`.
2. A manifest capping events per generation bounds emitted events accordingly, with identical
   truncation order across runs at the same seed.
3. The pattern store round-trips: an unrecorded technique returns success rate `1.0`, an
   always-detected technique returns `0.0`.
4. `swarmctl red-swarm score --json` prints `red_fitness`, `evasion_rate`, `stealth`, and
   `events_emitted` as top-level fields.

## Global constraints

Carried verbatim from phase 288 (`288-01-PLAN.md` "Global constraints") except where 289 extends
them. All still bind:

- Root toolchain (Rust 1.97.1, edition 2024); `cargo fmt --all`; `cargo clippy --workspace
  --all-targets -- -D warnings`; `unwrap_used`/`expect_used` denied outside `mod tests`; no
  `panic!`/`todo!`/`unimplemented!`; `tools/check-runtime-panic-contract.sh`,
  `tools/check-workspace-layering.sh`, `tools/check-visibility-baseline.sh` and
  `tools/check-gates-wired.sh` stay green.
- **No new crate dependency.** JSON is `serde_json` (already pinned); no new PRNG, no `rand`
  beyond what 288 uses, no filesystem crate beyond `std`.
- **The red lane never reaches response authority** (ARMSCI-02 is Phase 291's gate; the rule
  binds now): nothing under `red_swarm/` names `execute_response`, `ResponseAdapter`,
  `PolicyDecision::Authorize` or `live_response`, imports `swarm_response`, or takes a
  `RuntimeEventBroadcaster`. Scoring reads a snapshot and a plan and returns numbers; the pattern
  db reads and appends a file; neither acts on anything.
- **Techniques are catalogued or they do not exist.** The scorer never invents a technique or a
  catch_rate; every number it emits derives from the plan's `GeneStep.technique` values and the
  `EvasionCoverageSnapshot` it is handed. A technique in the plan but absent from the snapshot is
  **uncovered** (catch_rate `0.0`), never an error — that is the exact case red is hunting for.
- **Determinism is a property, not a claim.** `AttackScorer::score` is pure: identical `(plan,
  snapshot)` produce a bit-identical `AttackFitness` (an `f64`-exact test, not epsilon, for the
  `0.0` and boundary cases). `StealthBudget::apply` is pure and order-preserving: identical
  `(steps, budget)` produce identical truncated output (SC 2). No wall clock touches any output.
- **No wall clock on an output path.** `AttackPatternDb` records a `generation` (an integer the
  caller supplies), never a timestamp; its file contents are a function of what was recorded, so
  two identical record sequences produce byte-identical files.
- Public items carry doc comments in the crate's voice (WHY, not WHAT). Tests are named
  `a_thing_does_x_when_y`. Commits are `git commit -s`, Conventional Commits subjects.
- The closing task updates only `.planning/ROADMAP.md` (phase 289 block: `Status: Complete`,
  `Plans: 289-01`), `.planning/REQUIREMENTS.md` (the four ATKSCORE rows to `[x]` with the
  commit), and `.planning/STATE.md` (position + one Memory line). Nothing else in `.planning/`.

**Pre-flight scan (controller settles these before Task 1, records the ruling in the ledger):**
- **Where `stealth` becomes authoritative.** Task 1's `score` must satisfy SC 1 from
  `(plan, snapshot)` alone. Resolution: `AttackFitness.stealth` defaults to `1.0` (a plan within
  budget spends no stealth), so `red_fitness = evasion_rate * stealth` reduces to `evasion_rate`
  for SC 1. Task 2 supplies the authoritative `stealth < 1.0` when a plan exceeds its budget, and
  Task 4 threads it into the CLI. Task 1 therefore takes an optional `stealth` (default `1.0`),
  and does NOT depend on `StealthBudget`.
- **Budget is a post-plan pass, never in the planner.** `RedGenome::plan` stays the pure 288
  planner. `StealthBudget::apply(Vec<GeneStep>) -> BudgetOutcome` runs after planning. Task 2
  must not edit `genome.rs`'s planning path.
- **Truncation is tail truncation at first breach.** Walk steps in final order; admit while all
  three caps hold; the first step that would breach any cap stops admission and every later step
  is dropped (matches 288's contiguous-survivor semantics). This is the deterministic reading of
  "truncates once exhausted."

### Task 1: `AttackScorer` and `AttackFitness` (ATKSCORE-01, SC 1)

**Files.** `crates/swarm-runtime/src/red_swarm/scoring.rs` (new); one `pub mod scoring;` line in
`red_swarm/mod.rs`. No other file.

**Types.**
- `#[derive(Debug, Clone, Copy, PartialEq, Serialize)] #[serde(rename_all = "snake_case")]`
  `pub struct AttackFitness { pub evasion_rate: f64, pub stealth: f64, pub red_fitness: f64 }`.
- `pub struct AttackScorer;` with
  `pub fn score(&self, plan: &RedPlan, coverage: &EvasionCoverageSnapshot, stealth: f64) -> AttackFitness`.
  (`stealth` is the budget-supplied factor; callers with no budget pass `1.0`. Consider a
  `score_unbudgeted(plan, coverage)` convenience that passes `1.0` — the SC-1 test uses it.)

**Behaviour.**
- For each `step` in `plan.steps`, resolve `step.technique` in `coverage`: find the technique's
  `AdversaryTechniqueCoverageReport` (search the snapshot's detector reports / technique reports —
  read `evasion_coverage.rs` for the exact traversal). Its **per-technique catch** is the catch
  across its mapped detectors: a technique is caught if any mapped detector catches it, so take
  the **max** `catch_rate` over the technique's occurrences/mapped detectors. A technique with no
  report is **uncovered**: catch `0.0`.
- `detector_weighted_catch_rate` = the mean of per-technique catch over the plan's steps (a plan
  with no steps scores catch `0.0` → evasion `1.0`; document that boundary). "Detector-weighted"
  is satisfied because each technique's catch already aggregates its mapped detectors; if the
  implementer instead weights each technique by its mapped-detector count, that is acceptable
  **only if SC 1 still holds exactly** — the SC-1 test is the arbiter.
- `evasion_rate = 1.0 - detector_weighted_catch_rate`.
- `red_fitness = evasion_rate * stealth`.

**Tests** (build fixtures with `TargetGraph::from_parts`/hand-built `RedPlan`s and hand-built
`EvasionCoverageSnapshot`s — do not depend on the live repo corpus for the exact numbers):
- SC 1a: a plan whose every technique is `Detected` at catch `1.0` scores
  `red_fitness == 0.0` (assert exact `0.0`, and `evasion_rate == 0.0`).
- SC 1b: a plan built only from declared-uncovered techniques (each `NotCovered` / absent from
  the snapshot) scores `red_fitness > 0.5` (and `evasion_rate == 1.0`, `stealth == 1.0`).
- A mixed plan scores strictly between, and `red_fitness` scales linearly with `stealth`
  (`score(.., 0.5)` is half of `score(.., 1.0)`).
- Determinism: two `score` calls on the same inputs return the identical `AttackFitness` bits.

**Verification.** `cargo fmt --all --check`; `cargo clippy -p swarm-runtime --all-targets --
-D warnings`; `cargo test -p swarm-runtime red_swarm::scoring`.

### Task 2: `StealthBudget`, host binding, and `events_emitted` (ATKSCORE-02, SC 2)

**Files.** `crates/swarm-runtime/src/red_swarm/budget.rs` (new); one `pub mod budget;` line in
`red_swarm/mod.rs`. No other file (do NOT touch `genome.rs`'s planner).

**Types.**
- `#[derive(Debug, Clone, Copy, Serialize, Deserialize)]`
  `pub struct StealthBudget { pub max_events_per_generation: u32, pub max_distinct_hosts: u8,
  pub max_technique_repeats: u8 }` with a `DEFAULT` const (choose bounds that let the default
  24-step campaign pass without truncation, so SC-1 fixtures are unbudgeted; a *tighter* test
  budget drives SC 2).
- `pub struct BudgetOutcome { pub steps: Vec<GeneStep>, pub events_emitted: u32,
  pub stealth: f64, pub truncated: bool }`.
- `pub fn apply(&self, steps: Vec<GeneStep>) -> BudgetOutcome`.

**Behaviour.**
- Walk `steps` in final order, maintaining running totals: emitted events
  (`+= step.event_indices.len()`), the set of distinct bound hosts, and a per-technique count.
- **Host binding** (the 288 placeholder `host_slot = 0` becomes real): assign each admitted step
  a `host_slot` in `0..max_distinct_hosts` deterministically from the step's position/technique
  (a pure function of the step and the running state — never a RNG draw; the red lane draws no
  entropy). Document the assignment rule. Binding must not itself breach `max_distinct_hosts`.
- Admit a step only if, after it, all three caps still hold. The first step that would breach any
  cap stops admission; drop it and every later step (tail truncation). `truncated` records
  whether any step was dropped.
- `events_emitted` = total emitted events across admitted steps.
- `stealth` = a bounded factor in `(0.0, 1.0]` reflecting budget headroom: `1.0` when nothing was
  truncated, decreasing as more of the plan is dropped (e.g. `admitted_events /
  proposed_events`, clamped). Keep it a pure function of the admit/drop counts; document the
  formula. This is the `stealth` Task 4 feeds to `AttackScorer::score`.

**Tests.**
- SC 2a: a budget with `max_events_per_generation = N` bounds `events_emitted <= N`; a plan whose
  proposed events exceed `N` is truncated and the surviving prefix is exactly the first steps
  that fit.
- SC 2b: `apply` on the same `(steps, budget)` twice returns identical `BudgetOutcome.steps`
  (identical truncation order); and the bound holds for `max_distinct_hosts` and
  `max_technique_repeats` independently (a plan that repeats one technique past the cap truncates
  at the repeat, a plan that would touch too many hosts truncates at the new host).
- Host binding is within `0..max_distinct_hosts` for every admitted step and is deterministic.

**Verification.** As Task 1's, plus `cargo test -p swarm-runtime red_swarm::budget`.

### Task 3: `AttackPatternDb` (ATKSCORE-03, SC 3)

**Files.** `crates/swarm-runtime/src/red_swarm/pattern_db.rs` (new); one `pub mod pattern_db;`
line in `red_swarm/mod.rs`. No other file.

**Types.**
- `#[derive(Debug, Clone, PartialEq, Eq, Serialize, Deserialize)]`
  `pub struct AttackPatternRecord { pub generation: u32, pub technique: String, pub detector:
  String, pub detected: bool }`.
- `pub struct AttackPatternDb { … }` holding the records. IO is behind a seam so unit tests use
  an in-memory buffer, not a tempfile:
  - `pub fn from_reader(r: impl BufRead) -> Result<Self, RedSwarmError>` — parse JSONL, one record
    per line, tolerant of a trailing newline; a malformed line is a `RedSwarmError` (fail closed).
  - `pub fn append(&mut self, record: AttackPatternRecord)` — in-memory append.
  - `pub fn write(&self, w: impl Write) -> Result<(), RedSwarmError>` — serialise JSONL,
    append-only order preserved; byte-identical for an identical record sequence.
  - `pub fn technique_success_rate(&self, technique: &str) -> f64`.
- A thin `pub fn append_line(path, record)` / `load(path)` file wrapper over the reader/writer for
  the CLI; **no file IO inside unit tests**.

**Behaviour.**
- `technique_success_rate(t)` = `(count of records for t with detected == false) / (count of
  records for t)`. **An unrecorded technique returns `1.0`** (never seen = never caught = fully
  successful, the optimistic prior that lets a new technique be tried). A technique every record
  marks `detected == true` returns `0.0`.
- This rate is what a later generation reads to bias its operators (the *bias wiring* into the
  operators is Phase 290's co-evolution loop, COEVOLVE-03/-04; Task 3 delivers the store and the
  rate, and a doc comment says so — do not reach into `operators/` here).

**Tests.**
- SC 3a: a fresh db returns `technique_success_rate("T1055") == 1.0` (unrecorded → `1.0`).
- SC 3b: a db where every record for a technique has `detected == true` returns `0.0`.
- A mixed case (2 of 4 detected) returns `0.5`.
- Round-trip: `write` then `from_reader` reproduces the records; the file bytes are identical for
  an identical record sequence (no timestamp, no map ordering).
- A malformed JSONL line is a `RedSwarmError`, not a panic.

**Verification.** As Task 1's, plus `cargo test -p swarm-runtime red_swarm::pattern_db`.

### Task 4: `swarmctl red-swarm score --json` (ATKSCORE-04, SC 4)

`crates/swarm-cli/src/core.inc` (add the `score` subcommand). Match the existing `plan` command's
structure exactly — read `red_swarm_cmd.rs` first.

**Behaviour.** `swarmctl red-swarm score --seed <u64> --generation <u32> --campaign <name>
--coverage <path> [--catalog <path>] [--suite <path>]... --virtual-clock-start-ms <i64>
[--max-events <u32>] [--max-hosts <u8>] [--max-technique-repeats <u8>] [--json]`:
1. Build the graph and plan exactly as `plan` does (reuse the shared helper; do not duplicate the
   graph-loading logic).
2. Apply `StealthBudget` (from the `--max-*` flags, else `StealthBudget::DEFAULT`) → the emitted

4. Score with `AttackScorer::score(plan_after_budget, coverage, stealth)`.
5. `--json` prints an object with **top-level** `red_fitness`, `evasion_rate`, `stealth`,
   `events_emitted` (plus a `determinism` object mirroring `plan`, for reproducibility). The
   human form prints a short table.
- Same determinism contract as `plan`: refuse without `--virtual-clock-start-ms` (exit 1);
  byte-identical `--json` output across two runs at the same inputs.

**Tests** (the crate's existing CLI test pattern — `grep -rn 'assert_cmd\|Command::cargo_bin\|
run_swarmctl' crates/swarm-cli crates/swarm-runtime-http`):
- SC 4: `--json` output parses and has the four top-level fields, all finite.
- A fully-caught coverage fixture yields `red_fitness == 0.0`; an all-uncovered fixture yields
  `red_fitness > 0.5` (SC 1 end-to-end through the CLI).
- Determinism: two invocations at the same inputs are byte-identical.
- Refusal: omitting `--virtual-clock-start-ms` exits 1 with the same message shape as `plan`.
