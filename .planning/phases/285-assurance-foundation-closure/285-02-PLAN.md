The generic store cannot call `WitnessCandidateVerifier::verify_prepare`: the exact CAS DTO deliberately has no candidate request, session authorization, request digest, or verified abort outcome. Candidate verification remains the public-service responsibility in Plan 04. Plan 02 proves the seam with a signed envelope produced from `prepare_verified_candidate`, then independently calls `validate_store_transition` against the authenticated current entry before mutation.

Ready initialization creates every admitted key with a signed empty envelope, and `InspectReady` requires exact equality with the admission-derived key set. A missing admitted key is corruption and an unconditional readiness refusal, never an authenticated absent-stream application outcome. Plan 02 must not add a `VerifiedWitnessStoreStateV1(None)` constructor; `from_present` remains the only admitted-request construction path.

The lower-level `WitnessStoreReadyResultV1` is static readiness metadata only: configuration, epoch, anchor, admission set, signed Ready manifest, creation time, and explicit deployment bounds. It must not contain a revision, state digest, envelope, `validated_streams`, or any other dynamic per-entry summary. Revisions are unsigned transport observations and cannot become authenticated by comparing two fields returned by the same backend. For proxy `InspectReady`, first validate the static readiness result, then call `read_entry` exactly once for every admitted stream in sorted order, authenticate each returned stream ID, revision, signed envelope, initialization digest, component bounds, and admission mapping, and construct the wire `validated_streams` map exclusively from those reads. Any missing, duplicate, foreign, corrupt, or count-mismatched read refuses the whole response. Tests must kill coordinated mutants that alter both a backend summary and its claimed revision; backend-supplied dynamic summaries are forbidden rather than cross-checked.

Capacity validation consumes an explicit `WitnessStoreDeploymentInputsV1 { max_manifest_bytes, maximum_admitted_streams, configured_replica_count }`. It requires the signed Ready manifest's actual canonical byte length to be at most `max_manifest_bytes`, the admitted count to be nonzero and at most `maximum_admitted_streams`, and the bucket replica count to equal `configured_replica_count`. The exact checked bucket formula uses `max_manifest_bytes`, `maximum_admitted_streams`, and the maximum admitted retained-entry bound as distinct inputs; it never substitutes response size or the current admission count.

The reference model is a second state machine, not a wrapper around production validation. It may share only public DTO definitions, canonical JSON, domain-separated hashing, and raw Ed25519 verification primitives. A source-level guard rejects calls to production envelope validators, admission helpers, candidate/head constructors, `validate_against_prepared`, `validate_store_transition`, `validate_cas_transition`, `InMemoryWitnessStore`, or `WitnessAtomicStore`. It independently validates every Ready field/signature/relation/deployment bound and every initial/read envelope before returning a positive result. One table drives the complete genesis, rotation, sealed Prepare, commit, abort, read, conflict, exact observation, re-signed content/stale-session/admission, size/capacity, pre-CAS crash, and lost-after-CAS corpus through production and reference transitions, with normalized results and end-state bytes compared. Executable mutated stores for both generation and commit/abort semantics must be accepted by their broken transition paths and rejected by the independent model.

Store-proxy requests are signed by the witness key. Store-proxy responses have no governance signature and rely on the authenticated private service import; they bind the exact request digest and are independently validated by the public witness. Governance code carries logical revision and confirmation metadata only. Actual `KV-Operation`, expected-sequence, stream, and acknowledgement header construction and mutation belong exclusively to Plan 03B.
